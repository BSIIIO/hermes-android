## 3. 续作：怎么接着做

用户装机测 `app-arm64-v8a-release.apk`。收到截图后的标准动作：

1. **先定位，再改**。用 `scan_prose.py` + `grep` 找原文。若 grep 首轮不中，
   **几乎一定藏在三元分支 / 枚举构造 / 数据模型 switch 里** —— 读渲染链找根因，
   不要停在 widget 层。
2. **区分「漏扫」与「有意保留」**。对照 §1 表。命中保留清单就直接给理由，不改。
3. **跑死 key 扫描**（见下）—— 这是唯一能发现「carry-not-wire」类缺陷的手段，
   纯扫描器发现不了。**每批次 PR 前必跑。**
4. 纪律不变（§4）。每批一个 PR，CI 绿即合，再做下一批。

### 死 key 扫描（回购核实时新增的唯一有效手段）

carry-not-wire 的形态是：**key 写了、三处都对齐、中文翻译也有，但全仓没有一个调用点**。
`scan_prose.py` 看不见它，`flutter analyze` 也不报未使用的 public getter。
只有反查引用能发现：

```python
# 抽象类 685 个 key，逐一在 lib/ + test/ 全部 dart 文件里找引用
# 零引用 = 死 key = 要么该删，要么有未接线的调用点
```

回购核实跑出 **20 个死 key**，其中 **10 个**指向 PR #16 的真 bug（`activityGroup*` /
`activityTurn*` / `activityRunningNow` / `activityWaitingForYourInput` / …），
另 10 个确属废弃（`drawerProfile`、`chatsNewChat`、`cronNeverRun`、`uploadFailed`、
`activityDurationMilliseconds` / `Seconds`、`chatsSearchAiFullText` 等）——
**死 key 分两类，删之前必须逐个人工判断，不要一律清。**

## 4. 工程纪律（血的教训，务必遵守）

### CI 与版本

- `pubspec.yaml` / `pubspec.lock` **零改动**是硬约束。改 `version:` 行会触发
  `pr-quality.yml` 的 versionCode gate，所以 bump 必须同步三处：
  `pr-quality.yml`、`release.yml` 的 `REQUIRED_BASE_VERSION_CODE`、
  `test/release_identity_test.dart` 的**字面量断言**。
- `versionCode` 决定能否原地覆盖升级（arm64 split = base * 10 + 2，须 > 2127）。
- `flutter analyze --no-pub --fatal-infos`：**info 级 lint 也失败**。新 public 成员要 `///`。
  合并冲突解丢一个 `@override` 都会挂（见 §5 事故 13）。

### 本地工具链

```bash
export PATH=/vol2/@appdata/trim.hermes/workspace/flutter/bin:$PATH   # Flutter 3.44.0 / Dart 3.12.0
flutter analyze --no-pub --fatal-infos                                # 零问题才继续
bash /vol2/@appdata/trim.hermes/workspace/scripts/test-sharded.sh 240  # 88 文件 >420s，必须 background
```

分片结果在 `build/sharded-test-results/results.txt`，格式 `<exit_code> <path>`；
`awk '$1!=0'` 查失败。**JOBS=1 串行，绝不能用 `flutter test` 跑全套件**（会 wedged）。
`terminal(timeout=1)` 会杀掉分片并留下半份 results.txt —— 用 `background=true`
+ `notify=["SHARD_DONE"]`（见 §5 事故 14）。

### Git / PR

- 提交用 `git -c user.name="hermes-cto" -c user.email="cto@hermes.local" commit -F <file>`
  （禁 heredoc `-F -`，会被双写）。
- PR merge 用 PUT + `merge_method: merge`。`GITHUB_TOKEN` 在 `$HERMES_HOME/.env`。
- **操作前必 `git status` + `git branch --show-current`**，勿 `git clean`。
- **批次不能并行开分支**：第二个分支从 pre-#21 的 main 切出来，基就是脏的，
  PR 会 `mergeable_state: dirty`，必须 rebase 并解 `app_strings.dart` 追加冲突
  （见 §5 事故 12）。要么等前一批合完再切，要么 rebuild-onto。
- fork CI 在第一个 PR 被批准后会为后续 PR 自动跑，不必再等人工放行。

### 不可触碰的清单

`storageValue` 等持久化键、时长数字格式、wire 标识符、缓存键、grep 错误子串、
导出 markdown 骨架、debug 元数据、**发给 LLM 的 prompt**（用户明确定）、`HOME` 一级卡片标题。

### 中文化方法论

- **文案藏进 enum 构造或 model switch 的**（`TextSizePreference`、
  `ShareFavoriteAction.label`、`GatewayToolActivity.statusLabel`、`NewChatMode.label`、
  `ActivityGroupKind.title`）一律改为 `(AppStrings)` 函数/getter，**模型层不持有文案**。
  ⚠️ 改完必须 grep 一次 `.title` / `.label` 确认没有只改 getter 漏调用点的。
- **纯层无 context**（`new_chat_options`、`more_pane`、`buildSharedPrompt`、
  `buildActivityFeed`、`buildHomeDigest`、`buildHomeTurnSignals`）沿调用链传
  `required AppStrings s`，**不在数据类取 context**；`await` 前 hoist `s` 以避开
  `use_build_context_synchronously`。
  ⚠️ **传了参数 ≠ 用了参数**。`_classify` 收了 `s` 却一个字没读，
  编译器和 analyze 都不报「未使用的命名参数」。见 §5 事故 11。
- **绝不为测试写 mirror stub**（会静默漂移）。私有 widget 要测就抽成公开 widget
  （`_ThemeToggle` → `ThemeModeCard` 是范例）。
- **`AppStrings.of(context)` 出现在 `initState` 的 widget 不能套 `AppStringsScope` 测**
  —— Flutter 会抛 `dependOnInheritedWidgetOfExactType … before initState() completed`。
  `ChatScreen` 就是这种，所以 `chat_history_scroll_test` 断言英文回落值。
- **semantics label 与可见按钮文字可以是不同字符串**：voice composer 的
  Semantics 用 `voiceStop`（`Stop voice input` 整句，读屏用），按钮用
  `commonStop`（`Stop` 短词）。别为统一而牺牲任一层的可读性。

## 5. 本会话事故清单（反复踩过，别再踩）

1. **脚本改文件后用固定锚点重跑会重复加 key** —— 回滚文件会连带回滚同批 key，
   锚点数量变化。**批内 key 只加一次**；恢复文件后须显式重加该批 key。
2. **正则/脚本能把整个 `.dart` 写成 1 字节**（3 次：`home_digest_test.dart`、
   `quick_chat_lifecycle_test.dart`、`activity_feed_test.dart`）。**每次脚本改完必须
   `wc -c` + `grep -c 'void main'` 自检**，中了立刻 `git checkout <file>`。
3. **`app_strings.dart` 加 key 时插入声明行却丢值行** → analyze 报
   `body_might_complete_normally` / `missing_function_body` /
   `concrete_class_with_abstract_member`。改用按 **class 闭合括号前插入**的脚本
   `workspace/addkey.py`：`python3 addkey.py key "English" "中文"`（幂等，逐 key 跳过）。
4. **`.replace(o, n, 1)` 对零命中锚点是静默 no-op 却报成功** ——
   批处理脚本必须 `src.count(anchor) != expected` 就 `sys.exit`。
5. **`class_bodies` 正则必须匹配 `abstract class`**，否则 abstract 块被跳过、
   impl 插错 class（症状就是 §3 的 `concrete_class_with_abstract_member`）。
6. `ButtonSegment` 不是 Widget，不能 `widgetList<ButtonSegment>` /
   `find.descendant(of: ButtonSegment)` —— 从 `SegmentedButton` 子树抓 Text。
7. `gateway_activity.dart` 的 static `fromGatewayEvent` 曾险写 `const AppStringsEn()`
   强制英文 —— 改为必填参数由调用方传。
8. `chat_end_affordance` badge 用 `'1 new'`/`'N new'`，semantics 用
   `'1 new message'`/`'N new messages'` —— **两套不同字符串**，不能合成一个 plural key。
9. **CI artifacts 下载端点必须带 token 头**；不带会 302 后 401。run log 端点返回的 zip
   **尾部可能被截**，别依赖它取证，用 job/step 状态的 `conclusion` 作为权威证据。
10. **secret 状态是"我方历史判断"，会造成跨窗口失效** —— 动作前查一次
    `actions/secrets`，且这类环境事实必须写进 memory。
11. **「carry ≠ wire」是英文残留的最大单一来源**（本轮新发现，#21/#22 的根因）。
    `_classify` 签名里已有 `required AppStrings s`、`ActivityGroupKind.title`
    getter 返回字面量、`StatusChip` 的 `label ??` 回退全英文 ——三处都是
    **参数/数据结构已就位、值没接上**。静态扫描器一律失明，只有两件事能抓到：
    ① 死 key 反查引用；② 对同屏同类 widget 做 **diff**（Home 的 `title(s)`
    改了、Activity 的 `title` 没改 —— 同文件族的孪生实现对比）。
12. **批次分支不能基于旧 main 并行开**。#22 从 pre-#21 的 main 切出，
    两边都往 `app_strings.dart` 三个类的尾部追加 key，rebase 出 3 个追加型冲突。
    解法：三块都保留（纯追加不互斥），用 `python3` 按
    `<<<<<<< HEAD\n(a)=======\n(b)>>>>>>>\n` 模式统一 subn，
    且必须断言 `n == 3` 再写回；解完立刻 `flutter analyze`
    （本次即报出并补回 2 个 `@override`）。
13. **合并冲突解完必须 analyze**，不能只看"标记没了"。
    `@override` 被冲突解吃掉时报的是 `annotate_overrides`（info 级），
    在 `--fatal-infos` 下照样挂 CI。
14. **`terminal(timeout=1)` 会杀掉后台分片**并留下半份 `results.txt`
    （3/88 份，看着像"没有失败"）。必须 `background=true` + `notify=[...]`。

## 6. 发布链路（已跑通，可复用）

```bash
# 1. bump（versionCode 三处同步，见 §4）+ PR + CI + merge
# 2. tag 名必须等于 pubspec version：2.1.4+2144 -> v2.1.4
git tag -a v2.1.4 <main-sha> -m "<message>"
git push origin v2.1.4
# 3. release.yml 自动：校验 tag==version -> 签名 -> apksigner 指纹比对 -> 建 Release
```

- `workflow_dispatch`（在分支上）只构建 + 上传 artifact，**不建 Release**；
  只有 tag push 才触发 `Create Release`。
- run 日志：https://github.com/BSIIIO/hermes-android/actions/runs/36292349135（v2.1.4）
- 空跑基线：https://github.com/BSIIIO/hermes-android/actions/runs/36289552778
- **v2.1.5 尚未打**：#21/#22 只修文案，不动 `version:`；下次装机实测前若需带新包，
  再走一次 bump（三处同步）+ tag。
